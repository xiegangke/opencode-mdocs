## 评估范围

静态评估 `projects/remote/remote/bt_if/` 是否可改为由 `projects/remote/remote/tasks/task_btle.c/h` 实现。对比当前源码、构建清单，以及提交 `9e41e3c` 删除前的旧 `task_btle.c/h`。本轮未修改源码、未构建、未测试。

## 结论

结论取决于“使用 task_btle.c/h”的具体含义：

- **恢复旧 `task_btle.c/h`：不可行。** 旧实现依赖同期删除的 `btos_al.h/.c`、`btos_def.h`、`bt_stack_if_get_cb()` 和旧 `BT_OS_*` 消息协议。单独恢复无法编译；连同旧框架恢复会与当前 `bt_app_task + ls_ble_dispatch` 形成两套 BT task 和两套消息所有权模型。
- **将当前 BT task 核心实现移动或重命名为 `task_btle.c/h`：可行，推荐。** 必须保留当前唯一 BT task、FreeRTOS queue、`ls_ble` transport、异步请求所有权和 `ble_task_execute()` 的上下文约束。
- **将整个 `bt_if` 七个文件严格合并成两个文件：编译上可行，但不推荐。** 这会把任务调度、GAP 业务、profile callback、类型、配置和错误文本聚合到单一实现单元，扩大回归面，且不能解决低功耗生命周期等现有风险。

## 关键证据

- 旧 `task_btle.c` 只是 `btos_wait_event()`/`btos_task_create()` 任务壳，通过 `os_task_cb_t` 调用旧 `bt_stack_if`；旧头定义大量 `BT_OS_*` 消息 ID。
- 提交 `9e41e3c` 同时删除 `task_btle.c/h`、`bt_stack_if.c/h`、`btos_al.c/h` 和 `btos_def.h`，并新增 `mods/ls_ble/*` 及当前 callback/dispatcher 结构，说明它是架构替换，不是文件改名。
- 当前 `bt_app_if.c:630-657` 初始化 `ls_ble` transport、handler、BLE task 与 dispatcher；`:659-709` 是唯一 BT task 事件循环；`:675`、`:708` 仅在该任务中执行 `ble_task_execute()`。
- 当前 `bt_app_if.c:803-839` 对跨任务 app transaction 深拷贝 payload；`:82-96` 在 BT task 执行后释放。旧任务按消息 ID 统一释放的规则不能复用。
- callback 表位于 `bt_cb.c:53-59`、`:130-142`、`:154-188`；GAP/HID/OTA 等业务初始化与状态处理仍位于 `bt_app_if.c:289-611`，并非纯任务壳职责。
- CMake 和 Make 均已包含 `tasks/*.c`、`bt_if/*.c` 与 `mods/ls_ble/*.c` 及对应 include 路径，因此将当前任务实现移动到 `tasks/` 的构建组织条件已具备。

## 必须保留的运行时语义

1. 系统中只能保留一个 BLE executor task，不得恢复旧 `bt_os_task()` 后与 `bt_app_task` 并存。
2. `ble_task_execute()` 只能在该 BT task 内调用；ISR 和其他任务只能投递事件。
3. `ls_ble` 异步/同步请求与 app transaction 必须沿用当前各自的创建、复制、完成与释放规则，不能套用旧消息统一释放逻辑。
4. ISR schedule notify、stack transaction 和 app transaction 三类事件要继续进入同一 FIFO，避免协议栈执行与业务事务并发。
5. 启动顺序必须保留 dispatcher register/start、BLE pre-init/init、系统 ready event 和首次 `ble_task_execute()` 的相对关系。
6. 对外接口 `bt_app_stack_init()`、`bt_app_observer_register()`、`bt_app_transaction_post()`、`app_ble_connected_state()` 等应先保持符号兼容，避免同时修改大量业务调用方。

## 推荐迁移形态

### 第一阶段：低风险改名/移动

- 将 `bt_app_if.c/h` 的任务及公开接口实现移动或重命名为 `tasks/task_btle.c/h`。
- 先保持 `bt_app_*` API 名称和函数实现不变，只更新 include 和构建源文件归属。
- 保留 `bt_cb.c`、`bt_error.c`、`bt_common.h`、`bt_internal.h`、`bt_types.h`，不要为了“两文件”目标强行合并。
- 不恢复 `btos_al`、旧 `BT_OS_*` 消息 ID、`bt_stack_if_get_cb()` 或第二个任务入口。

### 第二阶段：按职责拆分

如果目标是减少 `bt_if`，可将任务/dispatcher/transaction 保留在 `task_btle.c`，把 GAP/profile 业务继续作为独立模块。文件数量不是正确性目标，线程和所有权边界才是。

### 第三阶段：运行时验证

经用户确认后，至少验证 CMake 与 Make 两个构建入口；随后验证启动、广播、连接/断开、配对、HID、语音、电量、OTA 和队列压力。

## 现有阻断风险

低功耗路径仍直接调用裸 `ble_task_sleep()`/`ble_task_init()`，绕过 dispatcher；`bt_stack_can_sleep()`、sleep callback 和 user schedule 仍未完整实现。该问题不会因移动到 `task_btle.c/h` 自动解决，也不应在关中断路径中直接改为无超时同步 dispatch。正式切换前应另行定义请求排空、BT task pause/resume、唤醒重初始化与 dispatcher 状态机。
