## 概述

`modules/adpcm-xq` 通过 CMake 构建静态库，并接入 `projects/remote/remote` 工程。当前只建立构建和链接依赖，尚未在业务代码中调用 ADPCM API。

## 构建规则

CMake 逻辑目标为 `adpcm-xq`，默认输出文件为 `libadpcm-xq.a`。静态库仅包含：

- `adpcm-lib.c`
- `adpcm-dns.c`

`adpcm-xq.c` 含命令行程序入口，不纳入静态库。CMake 检测数学库 `m`，remote 工程也在最终链接中保留系统数学库依赖。

## remote 工程接入

`projects/remote/remote/CMakeLists.txt` 使用带独立 binary directory 的 `add_subdirectory()` 引入模块，并将 CMake 目标 `adpcm-xq` 加入 `REMOTE_MODULE_LIBS`。因此即使业务代码尚未引用 ADPCM 符号，构建 remote 时也会先生成静态库；未被引用的静态库对象通常不会进入最终固件。

## 构建验证

使用仓库标准命令验证：

```sh
./build.sh remote
```

已使用 Nuclei GNU 14.2.1 交叉工具链构建成功。主要结果：

- CMake 构建目标显示为 `adpcm-xq`
- remote 工程构建成功并完成 OTA/flash 镜像打包
- 静态库产物：`build/projects/remote/remote/modules/adpcm-xq/libadpcm-xq.a`
- 归档成员仅有 `adpcm-lib.c.obj` 与 `adpcm-dns.c.obj`
- remote 最终链接依赖包含 adpcm 静态库目标和数学库 `m`

## 注意事项

模块仍保留独立 CMake 工程形式，没有改用仓库的 `create_module_library()`，所以归档位于模块自己的 binary directory，而不是 remote 的公共 `lib/` 目录。若后续需要在业务代码中使用 API，还应配置公共头文件 include 路径并增加实际调用。
